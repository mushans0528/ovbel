## 3. 多语言方案

多语言实现遵循以下既有文档：

- `docs/OVBEL网站开发实施方案.md`
- `docs/现有网站内容盘点与开发需求文档.md`

采用文档约定的语言前缀路由：

```text
/en/...
/zh/...
```

规则如下：

- 英文是默认语言；
- 访问 `/` 时跳转至 `/en`；
- 访问旧的无语言前缀路径时，跳转至对应英文路径；
- 英文与中文页面使用相同的产品分类和产品 slug；
- 语言切换保持在当前对应页面；
- 页面输出英文、简体中文和 `x-default` 的 alternate/hreflang 信息；
- 中文页面输出 `lang="zh-CN"`，英文页面输出 `lang="en"`。

示例：

```text
英文产品中心：https://ovbel.com/en/products
中文产品中心：https://ovbel.com/zh/products

英文产品详情：/en/products/conveyor-belts/chevron-conveyor-belt
中文产品详情：/zh/products/conveyor-belts/chevron-conveyor-belt
```

## 6. Cloudflare 构建问题与修复

### 6.1 问题现象

首次多语言提交触发 Cloudflare 构建后出现：

```text
ERROR Node.js middleware is not currently supported. Consider switching to Edge Middleware.
Failed: error occurred while running build command
```

### 6.2 原因

项目使用 Next.js 16。最初采用 `proxy.ts` 实现默认语言跳转，但 Next.js 16 的 Proxy 使用 Node.js Runtime，当前 Cloudflare OpenNext 不支持 Node.js Middleware，只支持 Edge Middleware。

### 6.3 修复

将：

```text
proxy.ts
```

改为兼容 Edge Runtime 的：

```text
middleware.ts
```

并将导出函数由 `proxy` 改为 `middleware`。路由跳转和语言请求头行为保持不变。

Next.js 16 会提示 `middleware` 文件约定已弃用，但这是当前 Next.js 16 与 Cloudflare OpenNext 组合下使用 Edge Middleware 的兼容方案。

## 9. 后续维护注意事项

1. 新增页面时应同时提供英文和中文内容，并保持 `/en`、`/zh` 路径一一对应。
2. 新增产品时，应同步维护英文产品数据和中文产品数据。
3. 所有站内链接必须携带当前语言前缀。
4. 修改语言路由后，应同时检查 canonical 和 hreflang。
5. 发布前至少执行一次 Next.js 构建和一次 OpenNext Cloudflare 构建。
6. 在 Cloudflare OpenNext 明确支持 Node.js Proxy 前，不应将 `middleware.ts` 再改回 `proxy.ts`。
7. GitHub 登录凭据应继续保存在系统钥匙串中，不应写入仓库或环境配置文件。
